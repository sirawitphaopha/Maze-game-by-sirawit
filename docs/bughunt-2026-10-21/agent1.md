## 1 · ส่งเกมที่ผังกำแพงปิดทางออกตาย เซิร์ฟเวอร์ค้างจนหน่วยความจำเต็มแล้วล้มทั้งตัว

**ความร้ายแรง** 🟠 (ต้องเข้าสู่ระบบก่อน แต่คนที่มีรหัสส่งคำขอเดียวก็ล้มเซิร์ฟเวอร์ได้ · ขัดหลัก "เซิร์ฟเวอร์ไม่เชื่อข้อมูลจากเบราว์เซอร์")

**ไฟล์:บรรทัด**
- `lib/game/level.ts:79-83` (`solveTo`)
```
  const p: number[] = [];
  let c = e;
  while (c !== s) { p.push(c); c = prev[c]; }
  p.push(s);
```
- `lib/maze/grid.ts:133-136` (`solve`) แบบเดียวกัน `while (c !== s) { p.push(c); c = prev[c]; }`
- `lib/server/games.ts:72-88` ตรวจแค่ว่าแกะผังได้ แล้วเรียก `replay` ทันที (`replay` → `newGame` → `solveTo` บรรทัดแรก ก่อนเดินสักก้าว)
```
  const maze = unpackWalls(size, exitX, walls);
  if (!maze) return { error: "ผังกำแพงเสีย" };
  ...
  const G = replay(settings, maze, events);
  if (G.status !== "won") return { error: "บันทึกการเดินไปไม่ถึงทางออก" };
```

**สถานการณ์ที่พัง**
1. เข้าสู่ระบบ แล้วส่ง POST `/api/games` ที่ `walls` เป็นผังที่ทางออกไปไม่ถึงจากทางเข้า (เช่นกำแพงปิดทุกด้าน `walls` ยาวแค่ 34 ตัวอักษรสำหรับ 10 × 10)
2. `unpackWalls` ไม่ได้ตรวจว่าเดินจากทางเข้าถึงทางออกได้ จึงผ่าน
3. `solveTo` ไล่ย้อนจากทางออก `prev[e]` เป็น -1 → `c = -1` → `prev[-1]` เป็น `undefined` → `c = undefined` ไม่มีวันเท่ากับ `s` → `p.push(undefined)` วนไม่รู้จบ
4. หน่วยความจำโตจนเต็ม บนเครื่องทดสอบ (Node ตัวเดียว) ทั้งเซิร์ฟเวอร์ล้ม · บน Cloudflare ตัวทำงานถูกตัดกลางคัน คำขออื่นที่อยู่ในตัวเดียวกันอาจพังไปด้วย (ส่วนบน Cloudflare ยังไม่ได้ลองจริง) · ด่านตรวจ `G.status !== "won"` ไม่เคยได้ทำงาน

**พิสูจน์แล้ว** `bughunt\p1_unreachable.ts` ใช้ `unpackWalls` `unpackMoves` `replay` ตัวเดียวกับเซิร์ฟเวอร์ · ผังผ่านตัวแกะ (`true`) → พิมพ์ "เริ่ม replay ..." แล้ว Node ล้มด้วยหน่วยความจำเต็มใน 1.2 วินาที (exit 134 · `Mark-Compact ... allocation failure`) ไม่ถึงบรรทัด "replay จบ"
(ไม่ได้ยิงเซิร์ฟเวอร์ทดสอบจริง เพราะจะทำให้เซิร์ฟเวอร์พอร์ต 3600 ล้ม)

**ทางแก้** ใน `gameRow` หลังแกะผัง เรียก `distFrom(n, R, B, s)` แล้วปฏิเสธถ้า `d[e] < 0` ("ผังกำแพงเสีย") · และให้ `solveTo` กับ `solve` หยุดเมื่อ `prev[c] < 0` (คืนทางว่างหรือโยนข้อผิดพลาด) กันวนไม่รู้จบทุกที่ที่เรียก รวมหน้าใบงาน `components/print/WorksheetView.tsx:152`

## 2 · ฐานข้อมูลสะดุดชั่วคราว เกมที่รอส่งอยู่ในเครื่องถูกลบทิ้งถาวร และเกมที่เพิ่งชนะไม่เข้าคิว ทั้งที่เซิร์ฟเวอร์บอกว่า "ลองใหม่ภายหลัง"

**ความร้ายแรง** 🟠 (ต้องมีฐานหรือด่านหน้า Cloudflare สะดุดก่อน แต่ผลคือเกมหายถาวร ไม่ใช่แค่ส่งช้า · มีแถบแดงบอก จึงไม่เงียบทั้งหมด)

**ไฟล์:บรรทัด**


- `lib/net.ts:58-62` ตอบ 200 แต่ไม่ใช่ JSON ก็นับเป็น "server"
- `lib/games.ts:187-192` (`uploadGame`) "server" = ไม่เข้าคิว
```
  if (r.why === "offline" || r.why === "timeout" || r.why === "nodb" || r.why === "auth") {
    ...
  }
  return { ok: false, queued: false, reason };
```
- `lib/games.ts:209-212` (`flushPending`) "server" = ลบออกจากคิวทันที
```

      drop(item.rec.saveKey);
      rejected.push({ label: item.rec.label, reason });
    }
```
- ฝั่งเซิร์ฟเวอร์ `lib/server/games.ts:31-34` ตอบ 500 ทุกครั้งที่ฐานมีปัญหา พร้อมข้อความ "ฐานข้อมูลไม่ตอบกลับ ลองใหม่ภายหลัง" · `app/api/games/route.ts:27` "ฐานข้อมูลไม่รับข้อมูล ลองใหม่ภายหลัง"

**สถานการณ์ที่พัง**
1. ชนะเกมตอนเน็ตหลุด เกมเข้าคิว "รอส่ง 1 เกม บันทึกไว้ในเครื่องนี้แล้ว"
2. เน็ตกลับมา แต่ Supabase สะดุด (หรือตัวทำงานบน Cloudflare ล้ม ตอบ 500 · หรือด่านหน้าตอบ 502 504)
3. แถบรอส่งยิงเอง ได้ 500 → `flushPending` ลบเกมออกจากเครื่อง ขึ้นแถบแดง "ระบบไม่รับข้อมูล 1 เกม" · ไม่มีทางส่งซ้ำอีก
4. ระหว่างฐานสะดุด ชนะเกมใหม่ → การ์ดขึ้นแดง "บันทึกไม่สำเร็จ" เกมนั้นไม่ถูกเก็บในเครื่องเลย ทั้งที่ข้อความจากเซิร์ฟเวอร์บอกให้ลองใหม่ภายหลัง
5. สถานการณ์นี้คือสิ่งที่คิวรอส่งถูกสร้างมาเพื่อรับมือ (ฐานไม่พร้อม) แต่คิวกลับทิ้งของ · ขัดสกิล offline-resilience ข้อ ⑤ "ห้ามหยุดลองเองเมื่อครบจำนวนรอบ ของที่ค้างต้องพยายามส่งจนสำเร็จหรือจนผู้ใช้สั่งทิ้ง"

**พิสูจน์แล้ว** `bughunt\p2_queue_drop.ts` (จำลอง localStorage กับ fetch ไม่ยิงเซิร์ฟเวอร์จริง เรียก `uploadGame` `flushPending` ของจริง) ผล
```
[500 ฐานสะดุด] ตอนเน็ตหลุด queued=true คิว=1 → ลองส่งแล้ว sent=0 failed=0 rejected=1 คิวเหลือ=0 | เกมใหม่ queued=false reason="ฐานข้อมูลไม่รับข้อมูล ลองใหม่ภายหลัง" คิว=0
[502 ด่านหน้า Cloudflare] ... rejected=1 คิวเหลือ=0 | เกมใหม่ queued=false reason="ระบบปฏิเสธข้อมูล" คิว=0
[200 หน้าล็อกอิน Wi-Fi] ... rejected=1 คิวเหลือ=0 | เกมใหม่ queued=false
```
(กรณีหน้าล็อกอิน Wi-Fi ตอบ 200 เป็นหน้าเว็บ เกิดได้ยากบน https เพราะส่วนมากจะเป็นใบรับรองผิดแล้วกลายเป็น "offline" แทน · กรณี 500 502 504 เกิดได้จริง)

**ทางแก้** แยก "เซิร์ฟเวอร์ตรวจแล้วปฏิเสธข้อมูล" (400 413 · ส่งกี่รอบก็ได้คำตอบเดิม) ออกจาก "เซิร์ฟเวอร์มีปัญหา" (500 ขึ้นไป · 200 ที่ไม่ใช่ JSON) · ให้ `net.ts` ตั้ง `why` แบบใหม่เช่น "retry" สำหรับ 5xx และ JSON เสีย แล้ว `uploadGame` กับ `flushPending` ใส่คิวและลองซ้ำตามรอบปกติ · ทิ้งจากคิวเฉพาะ 400 413 · หรือให้ `dbFail` ตอบ 503 แทน 500 (แต่ต้องแก้ข้อ 3 ด้วย)

## 3 · ประตูยังไม่ได้ตั้งรหัส หน้าเว็บกลับบอกว่า "ยังไม่ได้ตั้งค่าเชื่อมฐานข้อมูล"

## 5 · ตัวตรวจเกมขาเข้ารับของที่ฐานจะปฏิเสธ (ได้ 500 แทน 400) และรับเกมที่ไม่มีทางเกิดจริง

- บัตรผ่าน ลายเซ็นผูกกับรหัสและความลับ แก้เวลาเองไม่ได้ · เทียบแบบใช้เวลาเท่ากัน · บัตรจากอนาคตเกิน 1 นาทีถูกปฏิเสธ · เปลี่ยนรหัสแล้วบัตรเก่าใช้ไม่ได้ทันที · คุกกี้ httpOnly SameSite=Lax (คำขอข้ามเว็บแบบ POST DELETE ไม่แนบคุกกี้ · workers.dev อยู่ในรายชื่อโดเมนสาธารณะ เว็บอื่นบน workers.dev นับเป็นข้ามเว็บ)
- รายการยกเว้นใน matcher เป็นการเทียบขึ้นต้น (`/icon.svgอะไรก็ได้` ข้าม middleware) แต่ไม่มีหน้าหรือเส้นทางหลังบ้านที่ขึ้นต้นแบบนั้น และหลังบ้านมีด่านสองกันอยู่ · `readCookie` โยนข้อผิดพลาดถ้าคุกกี้เข้ารหัสเพี้ยน แต่ middleware ปฏิเสธคุกกี้แบบนั้นก่อนเสมอ จึงไม่เกิดจริง
- กุญแจลับไม่หลุดไปฝั่งเบราว์เซอร์ ค้นค่าจริงของ `SUPABASE_SERVICE_ROLE_KEY` `MAZE_PASSWORD` `MAZE_AUTH_SECRET` ในไฟล์ฝั่งเบราว์เซอร์ 110 ไฟล์ (`.next/static` `.open-next/assets`) ไม่เจอ (ไม่ได้พิมพ์ค่าออกมา) · ไม่มี `NEXT_PUBLIC_` · `supabaseAdmin.ts` กับ `server/games.ts` มี `import "server-only"`
- ข้อความผิดพลาดจากฐานไม่ส่งกลับหน้าเว็บ (`dbFail` จดลงบันทึกเซิร์ฟเวอร์ ตอบข้อความกลาง) · `/api/status` ไม่ส่งที่อยู่หรือกุญแจ
- ลบ = ประทับ `deleted_at` เฉพาะแถวที่ยังไม่ลบ นับแถวจริงจาก `.select("id")` · ลบซ้ำตอบสำเร็จ · ไม่มีแถวตอบ 404 · ไม่มีทางลบแถวอื่นเพราะรหัสยึดจากเส้นทางและตรวจรูปแบบ UUID
- `save_key` ซ้ำ ใช้ upsert แบบไม่ทับ แล้วอ่านรหัสเดิม · ส่งพร้อมกันสองคำขอก็ได้แถวเดียว (ดัชนี unique ในฐาน)
- กับดัก 1,000 แถวของ Supabase ไม่มี รายการแบ่งหน้าละ 50 ด้วย `.range` พร้อม `count: "exact"` · ดัชนี `mz_games_played_idx` ตรงกับเงื่อนไขของรายการพอดี · การ์ดสรุปคิดจากหน้าเดียว แต่มีบรรทัดบอกไว้แล้ว (`HistoryView.tsx:161`)
- `scripts/sql/001_mz_tables.sql` เปิด RLS ถอนสิทธิ์ anon กับ authenticated ทั้งตาราง ลำดับเลข และฟังก์ชัน · ฟังก์ชันตัวดัก `set search_path = ''` ไม่ใช่ security definer · เงื่อนไขในฐานตรงกับตัวตรวจฝั่งเซิร์ฟเวอร์ (ระดับ วิธี ทางหลอก 3 ถึง 20 ทางวน 0 ถึง 4 ผัง 1 ถึง 2,000 ตัวอักษร บันทึก 200,000 ตัวอักษร)
- เวลาตรวจหนึ่งเกมจริง ยาวสุดตามสเปก (ด่านโหด 3,099 ก้าว) 2 ถึง 4 ms ไม่ชนเพดาน CPU ของ Cloudflare (`bughunt\p13_cpu.ts`)
- อ่านข้อมูลขาเข้าทั้งก้อนก่อนเช็กขนาดเมื่อไม่มี content-length แต่ทำหลังตรวจบัตรผ่านแล้ว คนนอกใช้ทางนี้ไม่ได้

**คิวรอส่งและเน็ตหลุด** (`lib/games.ts` `lib/net.ts`)
- ส่งซ้ำได้แถวเดียว (รหัสก้อนเดิมทุกรอบ ทั้งตอนลองซ้ำในการส่งครั้งแรกและตอนส่งจากคิว)
- เก็บลงเครื่องไม่ได้ ตอบ `queued: false` ตามจริง (ข้อ 16 ของรายงานเดิมแก้ถูกแล้ว)
- ลองซ้ำไม่วนไม่หยุด ตัวจับเวลาถอยห่าง 20 40 80 160 300 วินาที เพดาน 300 · ฐานยังไม่ตั้ง 300 วินาที · บัตรหมดอายุหยุดรอจนเข้าสู่ระบบใหม่ · กันส่งซ้อนในหน้าเดียวด้วย `busyRef`
- แก้คิวทีละรายการ อ่านของล่าสุดก่อนเขียนทุกครั้ง (เกมที่เข้าคิวระหว่างกำลังส่งไม่หาย ในแท็บเดียว)
- รายการอายุเกิน 30 วัน หายจากคิวโดยไม่แจ้ง ตรงตามที่สเปกเขียนไว้ (ตั้งใจ)
- `newKey` มีทางสำรองตอนเปิดผ่านเลขเครื่องในวงแลน (ไม่มี `randomUUID`) ตามสกิล offline-resilience
